# Q-04: Small finish

Five small fixes to the map's chrome. Checked on the `atlas:publish:next` build served by
`atlas:serve:next` (Lantern Road, Oskmark), in a fresh Chromium profile, at 1440x900 and 375x812.
Shots: `docs/polish-2026-11/shots/q04-*.png`.

## 1. Sea seams

- **Cause:** each of the three wave layers was a tiled background (80, 120 and 60 px wide) holding a
  slanted `repeating-linear-gradient`, slid with `background-position`. A slanted stripe does not
  line up across a vertical tile edge, so every tile edge showed a seam. All three layers met every
  240 px, which made the visible seams there. On a phone the same edges read as light bands.
- **Change (`src/atlas/ocean/OceanBackground.tsx`):** each layer is now one untiled gradient. It is
  wider than the sea by one horizontal stripe repeat (`period / sin(angle)`: 122.97, 144.15 and
  107.47 px) and starts that far to the left. It moves by `transform: translateX(0 → repeat)`, which
  lands on an identical picture, so the loop has no jump. Stripe angle, spacing, crest colour and
  opacity are unchanged, and the durations are scaled so the drift speed in px/s is the same.
  Moving by transform is done by the compositor with no repaint. The cost is GPU memory instead
  (numbers below).
- **Motion off:** how the sea stops depends on the view:
  - v2 (the shared canvas) passes `reduceMotion`, so the inline style is `animation: none`.
  - v1 (`AtlasViewer`) and the editor pass no prop. There the component's own CSS stops it: its
    `<style>` holds `:root[data-calm="true"] .ocean-wave-n { animation: none !important }` and the
    same for `prefers-reduced-motion`. The global `index.css` rule (`animation-duration: 0.001ms`
    under calm or reduced motion) also applies.
  - In the browser, setting `data-calm` on `<html>` outside React, with the inline animation still
    in place, turned the computed `animation-name` from `ocean-bg-drift-1` to `none`. So the CSS
    path that v1 and the editor rely on works. A v1 map itself was not opened.
- **Layer cost (review fix):** measured with CDP `LayerTree` in headless Chromium, with frame
  times from `requestAnimationFrame` over 3 s. "main" is main's sea put back on the same page
  (tiles plus `background-position`).

  | Case                  | Wave layers (this branch)        | Wave layers (main) | Main-thread ms/s, branch vs main |
  | --------------------- | -------------------------------- | ------------------ | -------------------------------- |
  | Ocean, 1440x900 dpr 2 | 3: 1163/1185/1148x839, 46.9 MB   | none (repainted)   | 13.5 vs 15.2                     |
  | Oskmark, 1440x900 dpr 2 | 3, 46.9 MB                     | none               | 16.3 vs 21.8                     |
  | Ocean, 375x812 dpr 3  | 3: 498/520/483x751, 40.6 MB      | none               | 13.3 vs 16.7                     |

  Frame p95 was 16.7–16.8 ms in every case on both versions (60 fps, no frames over 20 ms). The
  three layers together stay under the ~60 MB limit at 1440x900 dpr 2, so they were not cut. The
  cost is about 47 MB of extra GPU memory on a retina desktop, in exchange for no repaint.
- **Checked:** a column-gradient seam detector (scratch script) ran on 3 frames each at 1440 and
  375. Before, it found seams every 80 px on desktop and at 92/172/252/332 px on the phone. After,
  it found none. A side-by-side crop shows the same stripes. The existing canvas test (animation
  `none` under reduced motion) still passes.
- **Not checked:** a real GPU or a real phone (headless Chromium only), raster-thread time,
  and large screens. By the same sums, 2560x1440 at dpr 2 would be about 130–150 MB for the three
  layers; if that matters, the next step is fewer or shorter layers. Safari and Firefox not checked
  either.

## 2. One focus ring

- **Cause:** shadcn `Button`s use `ring-2 ring-ring ring-offset-2`. The crumbs had no focus style.
  Reset used the browser default. The Leaflet zoom buttons had a 2px inset outline.
- **Change:** `src/index.css` adds a new class, `.atlas-focus-ring:focus-visible`, and the
  `.leaflet-control-zoom a:focus-visible` rule. Both use the box-shadow that `ring-2 ring-offset-2`
  makes (`0 0 0 2px background, 0 0 0 4px ring`) with no outline. Zoom links get `z-index: 1` so the
  ring is not covered by the button next to them. The crumbs (`MapBreadcrumb.tsx`), including
  "Earlier levels", and Reset (`AtlasViewer.tsx`) use the class. The crumb list's clip (`ol`,
  `overflow-hidden`) gets room for the ring: `py-1 -my-1 pl-1 -ml-1 pr-1`. Above, below and on the
  left the clip grows by 4 px; nothing overflows in those directions. On the right it stays at the
  nav's edge, and the ring's room comes out of the inside (`pr-1`). The first version used
  `p-1 -m-1`, which let a trail too long for the nav show 4 px past it on the right (review fix).
- **Checked:** computed styles in the browser for a crumb, a zoom button and Reset are identical:
  `rgb(14,17,22) 0 0 0 2px, rgb(223,163,73) 0 0 0 4px`, outline none. Screenshots of each focused.
  The deepest trail (Ocean > Quessaly > Oskmark > Brindlecross) was measured at 375, 414, 640, 768,
  1024 and 1440:
  - the clip's right edge equals the nav's right edge at every width;
  - the gap to the neighbours is 8 px or more;
  - at 375 a focused crumb shows the whole ring.
- **Found, not fixed (outside Q-04):** at 768 and 1024 the full trail is wider than the nav, which
  is 120 px at 1024. The crumbs don't truncate there, so the trail is cut mid-word at the nav's
  edge. This happens on main too.
- **Not checked:** v1 maps separately. The controls are the same components and CSS in v1, so the
  change applies there too, but no v1 map was opened in the browser.

## 3. Reset icon

- **Change:** lucide `Maximize2` (which reads as fullscreen) is replaced by lucide `Map` in
  `AtlasViewer.tsx`. The icon is `aria-hidden`. `aria-label="Reset map view"` and the tooltip are
  unchanged.
- **Checked:** a smoke test covers the name, the tooltip, the hidden icon and that it is `lucide-map`.
  Seen in the browser.

## 4. Places counter

- **Change (`WanderControl.tsx`):** the meter row gets a quiet pill: `rounded-full bg-background/85
  px-1.5` and a `ring-1 ring-inset ring-border`. The ring is drawn inside the box, so there is no
  layout shift.
- **Checked:** the Wander block measured the same before and after (desktop 12,828 101x60; phone
  12,738 101x62). Seen in the browser over the sea and over land.
- **Width:** the row stretches to the Wander button's width, so with "0 of 4 places" nothing moves.
  The pill's padding (6 px each side) does make the row's own minimum width 12 px larger. With a
  longer count (for example "120 of 140 places") the row can be wider than the button, and the
  block then grows by up to 12 px compared with main. Only the short count was seen in a browser.

## 5. Sound invite

- **Cause / scope:** the welcome invite stayed until it was dismissed. Its lifetime is local UI state
  in `SoundControl` and is not tied to sound state, so the sound logic is untouched.
- **Change (`SoundControl.tsx`):** after `INVITE_VISIBLE_MS` (12 s) the text and the ✕ fade out over
  600 ms. The invite then folds to a 40x40 speaker button ("Turn on sound", same tooltip text) that
  calls the same `enableSound`. With reduced motion or calm mode it folds at once, with no fade.
  Pointer over the invite or focus inside it holds it open; a fade that is in progress comes back.
  Dismiss still removes it entirely. The resume invite ("Tap to resume sound") is unchanged.
- **Hold (review fix):** hover and focus are two flags inside the invite (`hovered`,
  `focusWithin`), and it is held while either is true. A pointer that crosses the pill and leaves no
  longer releases a keyboard user's hold, which used to fold the invite under the focused button.
  The invite reports its hold through an effect, so unmounting releases it. A remounted invite
  starts unheld; before, a failed `enableSound` brought it back held and it never folded. If it
  ever folds with focus inside it, focus moves to the speaker button instead of dropping to the
  page.
- **Left as is (product call):** the folded speaker has no ✕ and stays for the session (until sound
  is turned on or the page reloads).
- **Overlap:** the boxes did not intersect (there was a 10 px gap). However, the invite's x range
  ran about 6 px over the scale bar, and its `shadow-md` reaches about 9 px below it. The desktop
  notice dock's `bottom` goes from 4rem to 4.5rem, which gives an 18 px gap. The phone is unchanged.
- **Checked:** unit tests (fake timers) cover: full, then fading, then folded; the folded button
  turns sound on and folding never does; calm mode folds straight away; hover and focus hold it
  open, also together (a pointer leaving while focus stays, and the reverse); a remount after a
  failed enable folds again; dismiss removes it. The two new tests fail against the first commit.
  The focus hand-off to the speaker has no test: holding on focus means the UI can't reach it. In the browser: full at 3 s, the speaker button at 14 s, no sound
  preference saved, and folded at 12.4 s under reduced motion.
- **Not checked:** actually hearing sound after a click on the folded button (it is the same handler
  as the full invite's).

## Visible changes beyond the five

- On desktop, the sound invite and other dock notices sit 8 px higher.
- The folded speaker button is new UI. It is shown only after the invite folds, has no ✕, and
  stays for the session.
- The places counter row can be up to 12 px wider when its count text is longer than the Wander
  button (see 4).
- Crumbs have 4 px less room on the right before they are cut (see 2).
