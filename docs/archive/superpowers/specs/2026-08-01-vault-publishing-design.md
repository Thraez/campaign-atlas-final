# Publishing from the vault — part 2

**Date:** 2026-08-01
**Status:** design, pending review
**Builds on:** `2026-06-16-obsidian-readonly-merge-design.md` (shipped 2026-06-17)
**Replaces:** `2026-07-31-vault-as-source-design.md` (withdrawn — see §2)

---

## 1. What this is, in plain language

The DM's world lives in an Obsidian vault of ~2,179 notes. Since June the atlas
can already read that vault and merge notes in. Three things still don't work:

1. **Nothing tells the DM which published notes have since changed in the vault.**
2. **Images in notes are silently thrown away.**
3. **Every sync pulls the whole vault into one table**, which is unusable at 2,179 notes.

This design covers exactly those three. Everything else about vault reading is
already built and is not revisited.

## 2. What already exists (and the correction that produced this doc)

The `2026-07-31` spec proposed building a vault reader, a config for vault paths
and folder filters, a "tick what publishes" panel, and type inference. **All of
that shipped on 2026-06-17** (`continuous-dev-done.md:189`). That spec was written
without discovering the June work, so it is withdrawn rather than kept as a
misleading alternative.

Shipped and load-bearing here:

| Piece | Where |
| --- | --- |
| Read-only vault reader, symlink-escape guarded | `handleVaultScanRequest`, `vite-plugin-atlas-save.ts:960` |
| Containment check | `isReadableVaultPath`, `src/atlas/save/sourcePathAllowlist.ts` |
| Ignore engine (picomatch, `nocase`) | `src/atlas/import/ignoreRules.ts` |
| Machine-local settings + sync map | `.local-atlas/editor-settings.json`, `.local-atlas/sync-map.json` |
| Sync UI | `src/atlas/sync/SyncPanel.tsx` |
| Merge with disk-wins ownership | `src/atlas/import/mergeImportFrontmatter.ts` |
| Per-row `included` staging table | `src/atlas/import/stagingState.ts` |
| Write-conflict guard (`baseHash`) | `src/atlas/import/buildImportChanges.ts:68` |

Three corrections from the review that this design inherits:

- **Visibility is fail-open at the build.** `build-atlas.ts:425` defaults a note
  with no `atlas.visibility` to **player**. The June design (§3.5, §5.7) already
  handles this: visibility is always resolved and written explicitly, and new
  entities default to `dm`. **Nothing in this design may weaken that.**
- **Bare folder names are not globs.** Under both glob engines
  (`build-atlas.ts:222`, picomatch), `10_DmNotesAndSecrets` does **not** match
  `10_DmNotesAndSecrets/Secret.md` — only `10_DmNotesAndSecrets/**` does. Any
  folder rule this design introduces must be **generated by the UI**, never typed.
- **`check-image-privacy` does not know where an image came from.** It checks EXIF
  metadata and filenames against derived secrets (`check-image-privacy.ts:1-24`).
  It cannot stop a secret image being copied out. §5 handles that at the source.

## 3. Gap 1 — "which of my published notes changed?"

### The problem

`SyncMapEntry` stores `{ id, baseType }` (`syncMap.ts:1-7`). The only hash in the
system is `baseHash`, a SHA-256 of the **atlas-side** file used as a write-conflict
guard. Nothing records what the **vault** note looked like when it was published,
so the question "has Corven changed since I published him?" is unanswerable.

This matters more than anything else here: a lot of the vault is mid-rework, so
"show me only what actually changed" is the difference between a usable tool and
a 2,179-row table.

### Design

Extend the sync-map entry:

```ts
export interface SyncMapEntry {
  id: string;
  baseType: string;
  /** SHA-256 of the vault note's raw bytes at the last successful sync. */
  approvedHash?: string;
}
```

`.local-atlas/sync-map.json` is machine-local and gitignored — correct for this,
since it is a working aid, not published state. (The withdrawn spec proposed a
*committed* selection file; that was wrong, and would have fought the existing
machine-local settings.)

On each sync, per vault note:

| Vault hash vs `approvedHash` | State | DM sees |
| --- | --- | --- |
| equal | **unchanged** | hidden by default |
| different | **changed** | "changed since you published it" |
| no entry | **new** | "not published yet" |
| entry, note gone | **orphan** | informational, never auto-deleted (June §5.3) |
| `approvedHash` absent (pre-upgrade) | **unknown** | shown as changed once, then settles |

`approvedHash` is written only on a **successful** sync of that row, so a failed
or cancelled sync never marks a note as published.

**Rename detection, deterministically.** A note with no sync-map entry whose hash
**exactly equals** a known `approvedHash` at a different path is a moved/renamed
file. Offer "this looks like *Corven*, renamed — link them?" This is an exact-hash
match, not fuzzy resemblance, so it does not reopen the "no fuzzy matching"
decision in June §5.3; it feeds the existing manual rename-link affordance.

**Honest limit.** The hash tracks the *vault* side only. If the DM edits a note in
the atlas editor and later re-syncs a changed vault note, the vault content
overlays the atlas content per June §3.3. The existing `baseHash` guard prevents a
blind overwrite of an unseen file, but the DM should be told plainly when a change
would land on a note they have edited here. Surface it as a `needsReview` reason
(June §5.5 already models exactly this as an orthogonal flag).

## 4. Gap 2 — images

### The problem

`parseObsidian.ts:82` **deletes** `![[…]]` embeds from the body, and `:106` skips
them during link extraction. Images don't fail to arrive — they are actively
discarded. `handleVaultScanRequest` returns `.md` files only.

### Design

**Server-side copy, not a browser round-trip.** The dev server can see both the
vault and the assets folder. Sending image bytes to the browser as base64 and back
through `/__atlas/save` would inflate them ~33%, run into the 25 MB scan cap, and
pointlessly move megabytes through the UI. A new narrow read-only-source /
write-to-assets route does the copy directly.

**Resolution.** Obsidian resolves `![[picture.png]]` vault-wide by basename (with
relative-path resolution when the embed contains a `/`). Resolution is constrained:

1. the resolved path must pass `isReadableVaultPath` (already exists);
2. **the resolved path must not be inside an ignored or non-candidate folder.**

Rule 2 is the leak fix the withdrawn spec missed. A published note embedding
`![[cabal-lair-map.png]]` that resolves into `10_DmNotesAndSecrets/` must be
**refused and reported** — "1 image skipped: it's in a folder you haven't included"
— never silently copied. Silence here is how a secret map reaches players.

**Naming.** Copied images are named from the entity, not the source file:
`corven-1.webp`, not `the-cabal-lair.webp`. A vault filename can itself be a
spoiler, and `check-image-privacy` would flag exactly that filename shape. Naming
from the entity id makes the whole class impossible instead of detected later.

**Target + metadata.** Files land in `public/atlas/assets/images/`. The
`asset-binary` write allowlist currently permits `assets/maps/` only
(`vite-plugin-atlas-save.ts:368`) and must be extended. Copies go through the same
sharp metadata strip as other saved images, so EXIF/GPS never lands.

**Body rewrite.** `![[picture.png]]` becomes `![](/atlas/assets/images/corven-1.webp)`.
Oversized or unreadable images are skipped with a visible count and reason — never
a broken link, never a silent drop.

## 5. Gap 3 — browsing that fits a 2,179-note vault

### The problem

`openWithVaultScan` fetches **every** non-ignored `.md` in one request and pushes
them all into one staging table. The only filter is a newline textarea of globs the
DM types by hand (`SyncPanel.tsx:34-37`). At this vault's size that is unusable,
and a hand-typed deny-list is the fragile direction when `10_DmNotesAndSecrets`
exists.

### Design

**Pick folders, don't type globs.** A new read-only endpoint returns a folder
summary — names and note counts, **no file contents** — and the panel lists them
with tick boxes. The DM ticks `03_Entities`, `01_Lore`, `02_Regions`,
`04_Factions`, `09_Glossary`; the other ~1,900 notes are never fetched.

Stored alongside the existing settings:

```ts
interface EditorLocalSettings {
  vaultPath?: string;
  candidateFolders?: string[];  // NEW — folders the DM draws from
  ignoreGlobs?: string[];       // unchanged; advanced escape hatch
  lastSyncAt?: string;
}
```

The scan endpoint takes the folder list and walks only those. **The UI generates
the match patterns** (`<folder>/**`), so the bare-folder-name hazard from §2 cannot
occur — the DM never types a glob to get correct behaviour.

**Combined with Gap 1, the default view becomes "what changed and what's new"**,
not "everything". For this vault that is a handful of rows instead of thousands.

**Precision about what this is.** This is scale and noise, **not** the secrecy
boundary. Secrecy is held by visibility defaulting new entities to `dm` (June
§5.7) and by the DM explicitly raising visibility. Folder scoping reduces the
chance of a mistake; it is not what prevents a leak, and must not be described to
the DM as if it were.

## 6. Safety properties, and how each is proven

| Property | Test |
| --- | --- |
| An image inside an excluded folder never reaches `public/` | Published note embeds an image resolving into `10_DmNotesAndSecrets/` → copy refused, count reported, no file written |
| Copied images carry no camera/location metadata | Copy an image with EXIF GPS → output has none |
| Copied image filenames can't leak a name | Source `the-cabal-lair.png` → output named from the entity id |
| A note unchanged since publishing stays quiet | Sync twice with no vault edit → second run reports 0 changed |
| A reworked note is reported, never auto-applied | Edit an approved note in the vault → reported as changed; player output unchanged until the DM includes it |
| Folder scoping actually scopes the read | Scan with one candidate folder → notes outside it are never fetched |
| The vault is never written | Hash every vault file before/after a full scan + image copy + sync → unchanged |
| Visibility never silently becomes player | New entity from a vault note → written `visibility: dm` |

Every one must be **mutation-checked** — break the code deliberately and confirm
the test fails. Per the audio-prune lesson (2026-07-30), a regression test that has
never failed proves nothing.

## 7. Out of scope

- Writing anything back to the vault (unchanged from June §12)
- Vault deletions driving atlas deletions
- Dataview / templater / plugin-generated content
- Live file watching — state is computed on panel open and on sync
- Fuzzy rename matching beyond the exact-hash case in §3

## 8. Open questions

Neither blocks implementation.

1. Whether unchanged notes are hidden entirely or shown collapsed behind a
   "45 unchanged" line. Recommend collapsed — it reassures without adding noise.
2. Whether image copying runs during sync or as a separate step. Recommend during
   sync, since an entity and its picture arriving separately is the confusing case.
